# scoring ケースの補完

作成日: 2026-11-02

corpus の未確定項目を具体例で補完する。
変換器の局面復元・点数解釈と、corpus の情報保持・構造検査を分ける。

## 補完した仕様

- 暗槓の `called_tile_index` と `from_seat` は、どちらも `null`。
- 加槓は元のポンで鳴いた牌の位置と相手を保持する。
  追加した牌を `called_tile_index` に指定しない。
  `tiles` は追加牌を含む四枚であり、配列は元牌譜の順序を保持する。
- チー・ポン・大明槓・加槓の鳴いた牌と相手は必須とし、
  相手は和了者自身の席にしない。
- 槍槓時の `discarder_seat` は和了牌を提供したプレイヤーの席とする。
  通常の打牌がない和了でも、別の席フィールドを増やさず表現する。
- 不明な和了状況の理由は `situation_provenance.unknown_fields` に
  `{"ippatsu": "missing_events"}` のような辞書で保持する。
  キーは `input.situation` の項目名、値は空でない理由。
  `null` の項目には理由を必要とし、既知の値には不明理由を付けない。
  理由がなければ空辞書とする。

`unknown_fields` は初期 v1 の必須フィールドとする。
開発中の旧例のようにこのフィールドがないデータは拒否する。
既存の文書例とテスト fixture は空辞書を追加して更新した。
変換器は不明な項目を `false` に置き換えず、`null` と理由を保存する。
corpus は理由の対応を検査するが、イベントから再判定はしない。

暗槓は鳴いた牌・相手が存在しないため両項目を `null` にする。
加槓は追加牌も含めて四枚を保持するが、`called_tile_index` は元のポンの
鳴いた牌を指す。追加牌の位置を示すフィールドとしては使わない。
元の相手と鳴いた牌は変換器がポンの記録から復元する。

## 具体例と根拠

テストは `packages/corpus/tests/fixtures/` のファイルだけを読み込む。
文書や Git 管理対象外の `logs/` には依存しない。
実牌譜由来の ID はマスクし、合成例は `synthetic-` で始まる ID を使う。
合成例は `source.scoring_values.fixture_kind="synthetic"` と明示する。

| fixture | 種別と確認内容 |
| --- | --- |
| `synthetic-sanma-tsumo.json` | 手作成。三麻のツモ・抜き北二枚・赤牌・三席の支払い |
| `synthetic-ankan.json` | 手作成。暗槓の鳴き元は両方 `null` |
| `synthetic-kakan.json` | 手作成。元のポンの鳴き元と呼ばれた牌の位置を保持 |
| `majsoul-double-ron-first.json` | 実牌譜。和了順 1、席 3 の和了 |
| `majsoul-double-ron-second.json` | 同じ実イベントの和了順 2、席 0 の和了 |
| `synthetic-liability.json` | 手作成。責任払いの支払いを保持しつつ比較から除外 |
| `tenhou-kokushi.json` | 実牌譜。国士無双の記録された 0 符を保持して比較除外 |
| `synthetic-yakuman-ippatsu.json` | 手作成。一発が有効でも期待役には国士無双だけを保持 |

実牌譜のダブロンは雀魂 `records[577]` の `hules` を分けたもの。
`RecordNewRound` は 469、立直宣言・成立は 534・535、
席 3 のチーは 555、和了牌を提供した席 1 の打牌は 576 にある。
チーの配列 `2s,3s,4s` と、最後の牌が席 2 から来たことも進行記録で確認した。
記録と算術上の対応は次のとおり。

| 項目 | 最初の和了 | 二番目の和了 |
| --- | --- | --- |
| 和了者 | 席 3 | 席 0（親） |
| 符・翻 | 40 符 2 翻 | 40 符 5 翻 |
| 本場・供託を除く和了点 | 2600 | 12000 |
| 本場分 | 300 | 0 |
| 供託分 | 1000 | 0 |
| 和了者の収入 | 3900 | 12000 |
| 席 1 からの支払い | 2900 | 12000 |

両ケースのイベント全体の点数移動は同じ
`[12000, -14900, 0, 3900]` とする。
このイベント全体の値を単独の和了の支払いへコピーしない。
和了順は元の `hules` の順序であり、席順への並べ替えは行わない。
本例のボーナス配分は記録された点数移動から確認したもので、
他の牌譜にも「配列の最初に必ず支払う」という規則を仮定しない。

国士無双は天鳳の XML 子要素 1136 の `AGARI` を基にしており、
`ten="0,32000,5"`、`yakuman="47"`、点数移動の記録を確認した。
これにより、今回の天鳳サンプルでは実際に 0 符が記録されていることを確認できた。
雀魂の国士無双が 25 符になるかは、このサンプルには例がなく未確認のまま。
corpus は値を補正せず、記録があれば保持した上で比較除外にする。

合成例のルール確認には
[天鳳公式マニュアル](https://tenhou.net/man/#RULE) の段位戦・役一覧を参照した。
ただし、合成例の点数は実際の牌譜から抽出した期待値ではなく、
手作業で指定した構造確認用の値である。`mahjong` の出力から生成していない。
変換器の正確性を検証する際は、これらを実牌譜と同等の変換 fixture とみなさない。

- 三麻例は門前ツモ・平和・赤一枚・抜き北二枚の 5 翻、20 符。
  支払いは親 4000、もう一人の子 2000 として、総額 6000 を保持する。
- 暗槓・加槓例は白の槓と同じ純手牌を使い、
  門前の暗槓例を 70 符 2300 点、開いた加槓例を 40 符 1300 点とした。
- 責任払い例は大三元の子のロンに、本場 300・供託 2000 を加えたもの。
  放銃者 16000、責任者 16300、和了者の収入 34300 を保持し、
  `payments_by_seat` は `liability_payment` により比較除外とする。
  責任者の出典側の値は `source.scoring_values.paoWho=2` に保持する。
- 役満時の一発例は国士無双の牌姿を基に状況と供託を変更した合成例。
  `riichi="riichi"`、`ippatsu=true` と期待役の国士無双を独立して保持する。

## 識別・役名・互換性

ケース ID の元牌譜 ID 部分は、変換器で UTF-8 の percent encoding を行う。
Python では `urllib.parse.quote(log_id, safe="")` とする。
たとえば原値 `example:game%/1` は `example%3Agame%25%2F1` となる。
`source.log_id` は原値のまま保持する。文書・fixture の `<masked-log-id>` は
表示用プレースホルダーなので、その表記にはエスケープを適用しない。
corpus 自体は ID を生成・再構成せず、渡された ID を読み書きする。

`win_number` は局内全体の記録順で 1 始まり、`source.winner_index` は
一つの和了イベント内で 0 始まり。出典のイベント単位の違いは維持する。
複数ロンの可否と精算の優先順位は変換器のルール解釈に属する。
天鳳段位戦では三家和了は流局になるため、三人分の和了ケースを捏造しない。

役の ID は文字列として保持し、corpus は全役の閉じた enum を持たない。
今回の例では `menzen_tsumo`、`pinfu`、`tanyao`、`iipeikou`、
`yakuhai_haku`、`dora`、`aka_dora`、`nuki_dora`、`riichi`、
`kokushi_musou`、`daisangen` を使用する。
全役の出典 ID との対応表は変換器で実際の対応を実装する際に定める。
これは corpus の読み書きを妨げる未実装の形式制約ではない。

初期 v1 は未知の版・フィールドを拒否し、不足する必須フィールドを
黙って補完しない。今後、公開後の形式を変更する場合は版を更新し、
必要な移行処理を明示して実装する。v1 のまま異なる意味で解釈しない。

## テストリスト

- [x] 不明な状況と理由の対応を検査し、JSONL・gzip に保持する。
- [x] 暗槓・加槓の鳴き元を検査し、牌順を維持する。
- [x] 三麻ツモ・抜き北の例を保持する。
- [x] 実牌譜のダブロンを和了者ごとに分け、全体の点数移動を維持する。
- [x] 責任払いの例で支払いを比較除外として保持する。
- [x] 役満時の一発と国士無双の符の例を保持する。
- [x] これらを manifest 付きデータセットとして読み書きする。
- [x] 独立環境と静的検査を確認する。

各テストは対象ライブラリで期待値を計算せず、一件ずつ追加する。
実牌譜由来の例と手作成の例は区別して記録する。

`unknown_fields` が未定義として拒否される Red の後、モデルを追加した。
理由の欠落・空の理由・既知の値への理由が受理される Red を確認してから
対応する整合性検査を追加した。副露も、暗槓の鳴き元や、明副露の
未記録・自家の鳴き元が受理される Red を確認してから検査した。

## 確認結果

- 開発環境: 140 件成功、実 symlink のテスト 1 件スキップ。
- sdist と wheel の生成が成功。
- wheel をインストールした Python 3.10.22・3.15.2 の独立環境で、
  それぞれ 140 件成功、同じテスト 1 件スキップ。
- Ruff の lint・format、ty、差分の空白検査が成功。
- fixture の ID がマスク済みまたは合成 ID であることと、文書リンクを確認。

実牌譜由来の三件と合成の五件を、非圧縮・gzip の manifest 付き
データセットへ保存し、全フィールドが維持されることを確認した。
これらは corpus の表現と読み書きの検証であり、
未実装の変換器や `mahjong` 自体の正確性検証の完了を意味しない。
