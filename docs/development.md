# 実装・テスト方針

決定日: 2026-11-01

## workspace の開発環境

ルートは開発ツールを管理する非パッケージのプロジェクトとし、
`packages/corpus`、`packages/tenhou-converter`、`packages/validator` を
uv workspace のメンバーとしている。
ロックファイルと開発用の仮想環境はルートで共有する。
corpus の配布名・import 名は、ともに `corpus` である。
天鳳変換器の配布名・CLI 名は `tenhou-converter`、import 名は
`tenhou_converter` とする。

validator は `packages/validator/` に置き、配布名・CLI 名は
`mahjong-validator`、import 名は `validator` とする。
[設計](validator-design.md) に従い validator の最低 Python は 3.15 とし、
全メンバー用開発環境と共通ロックファイルの最低 Python は 3.15 とする。
corpus と tenhou-converter 自体の Python 3.10 以上の対応は維持する。
corpus・tenhou-converter の旧 Python 対応は、workspace ではなく独立した
wheel の環境で確認する。ルートの ty も開発環境の Python 3.15 を指定する。

ルートで次を実行すると、全メンバーと開発ツールをインストールできる。

```console
uv sync --all-packages --python 3.15
uv run --no-sync python -c "import corpus; print(corpus.__file__)"
```

静的検査とパッケージのビルドもルートから実行する。
`references/` は前身の参考コードなので静的検査の対象外とする。

```console
uv run --no-sync ruff check
uv run --no-sync ruff format --check
uv run --no-sync ty check
uv build --package corpus
uv build --package tenhou-converter
uv build --package mahjong-validator
```

単体テストはパッケージの `tests/` に追加し、
ルートの pytest を使用する。ルートから次を実行すると、
`packages/` のテストを収集する。

```console
uv run --no-sync pytest
```

一時ディレクトリが制限される環境では、
`--basetemp=.cache/pytest` を指定して workspace 内に作成できる。
全メンバーのテストには Python 3.15 を使う。

各パッケージの `tests/` には `__init__.py` を置く。
テスト間で共有する準備処理は `conftest.py` の fixture として提供する。
pytest は importlib モードと `consider_namespace_packages = true` を使い、
親ディレクトリを含めて同名の `tests`・`conftest` をメンバーごとに区別する。
共有 fixture はテスト関数の引数で受け取り、テスト用モジュールの相対 import は
使わない。テスト用コードは実行時パッケージに含めない。

workspace での import 確認に加え、機能追加時にはビルドした wheel を
クリーンな環境へインストールして、未宣言依存がないことも確認する。

## 基本方針

t-wada 氏が説明するテスト駆動開発（TDD）を基本とする。
参考は、同氏による Kent Beck の定義の翻訳と考察
[「テスト駆動開発の定義」](https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck)
とする。

以下の手順を開発の基本とし、後半に記すプロジェクト固有の
テスト方針と組み合わせて運用する。

## 実装の進め方

1. 変更する振る舞いを分析し、正常系・境界値・異常系や既存動作への
   影響をテストリストとして整理する。
2. リストから一件を選び、具体的な入力と期待結果を持つテストを書く。
   実行して、意図した理由で失敗することを確認する（Red）。
3. そのテストを通すための必要最小限の実装を行い、
   既存テストも成功することを確認する（Green）。
4. テストを成功させた状態で、必要に応じてテストと実装の構造を
   改善する。振る舞いを変える作業と構造を整える作業を分ける
   （Refactor）。
5. 発見したケースをリストに追加し、完了した項目を消し込み、
   対象とする変更のリストが完了するまで繰り返す。

テストリストは期待する振る舞いの一覧であり、
最初からすべてをテストコードにするものではない。
テストを書く際に利用側から API を検討し、
実装からの学びを設計へ反映する。
将来の用途だけを理由に、汎用化や抽象化を先回りしない。

不具合修正では、まず問題を再現するテストを追加して失敗を確認する。
既存の振る舞いを変えないリファクタリングでは、
既存テストが通ることを確認してから構造を変更する。

## このプロジェクトでの適用

以下は、本プロジェクトの責務に合わせた運用方針である。

- テストは外部から観測できる振る舞いを検証する。
  内部の関数分割や呼び出し順序を必要以上に固定しない。
- 期待値は仕様や独立して確認した牌譜の記録から定める。
  テスト対象の出力をそのまま期待値として採用しない。
  特に `mahjong` の正確性を検証する期待値を、同じ `mahjong` で
  計算して作らない。
- コーパスの往復読み書きだけでなく、明示したデータとの対応も
  検証する。reader と writer に共通する誤りを見逃さないようにする。
- 変換器には小さな牌譜 fixture を用い、牌・副露・場況・期待値の
  変換、欠落や不正入力の扱いを確認する。
- パッケージ内のテストに加え、牌譜からコーパスを経て
  検証結果を得る経路を少数の結合テストで確認する。
- 各パッケージのクリーンな環境でのインストール・実行も確認し、
  workspace の共有環境による未宣言依存を見逃さないようにする。
- 大規模コーパスによる検証と実時間の性能測定は、
  高速な開発用テストから分離する。
  計測処理のテストでは実時間の速さを合否基準にせず、
  必要に応じて制御可能な時計や実行対象を使う。
- カバレッジの数値やテスト件数自体を目的にしない。
  アサーションの削除や期待値の無根拠な変更で成功させない。

文書だけの変更では実装用のテストを追加せず、内容とリンクを確認する。
設定変更では、その設定が担うインストールや実行などを確認する。

## 作業結果の報告

振る舞いの変更時は、追加・変更したテスト、Red の確認結果、
最終的なテスト・必要なチェックの結果を簡潔に報告する。
実行できなかった確認があれば、未確認の範囲と理由を明記する。
