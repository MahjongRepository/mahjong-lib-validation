# 天鳳 converter の設計

作成日: 2026-11-02

[全体設計](architecture.md) に従い、天鳳の進行記録から
[corpus v1](corpus-design.md) の scoring ケースを作る。
ファイル入力・変換 API・CLI は実装済み。確認結果と残る検証項目は
[実装記録](tenhou-converter-implementation.md) を参照する。
以下の「採用する方針」と、末尾の「実牌譜で確認する事項」を区別する。
実装は [テストリスト](tenhou-converter-implementation.md) から一件ずつ進める。

## 目的と責務

- 一つの `AGARI` を一人分の `ScoringCase` に変換する。
- 計算入力の和了状況は進行から復元し、期待値は `AGARI` の記録から取得する。
  役一覧から立直・一発などの入力を逆算しない。
- 元牌譜を読み直さず検証できるケースと、変換の集計・診断を出力する。
- 牌譜のダウンロード、得点計算、`mahjong` の実行は行わない。
  牌譜の取得元に依存しない、ローカル入力の変換器とする。

### 名前

配布名・import 名・CLI 名は、ハイフンとアンダースコアの違い以外を
統一する。import 名だけに `mahjong_` を追加しない。
配布名・CLI 名は `tenhou-converter`、import 名は `tenhou_converter` に
確定する。二語で短く、入力元と変換器であることが分かる名前を採用した。
変換先が corpus であることは説明で補う。
将来の雀魂変換器にも同じ命名規則を適用する。

### 配置と依存

配置は `packages/tenhou-converter/` の `src/tenhou_converter/`、
ビルドは `uv_build`、対応 Python は corpus と同じ 3.10〜3.15 とする。
実行時依存は workspace の `corpus` のみとし、XML・gzip・CLI は
標準ライブラリを使用する。`mahjong`、validator、houou-logs に依存しない。
workspace メンバーとロックファイルに登録済み。

## 対応範囲と実装段階

| 段階 | 対応する内容 | 完了条件 |
| --- | --- | --- |
| 初期実装 | 完全な mjlog XML、四麻・三麻の赤あり・喰い断あり段位戦、scoring 出力 | 両人数の状況復元・全役対応・抜き北・精算・分割出力と失敗時の非公開を確認する |
| SQLite 対応 | houou-logs DB の牌譜 ID と内容の逐次読み出し | 対応スキーマと圧縮・格納形式を fixture で固定する |

初期実装にもチー・ポン・各種槓、赤牌、複合役満・数え役満、
ダブロン、責任払いの保存を含める。
実牌譜由来の確認と合成 fixture による確認を区別する。
複数ロン・責任払い・特殊な状況の実牌譜照合は、残る検証項目として明記する。
最初の縦の実装では単純な門前ロンから始め、初期実装全体へ広げる。

四麻・三麻は同じ入力探索で受け取り、牌譜ごとに人数を判別する。
個室・大会・テスト対局、赤なし・喰い断なしなどは
`unsupported_rules` で除外する。corpus v1 にルール差を表す項目がないため、
これらを同じ `tenhou-ranked-match` として出力しない。
未知の XML 版、未知のイベント・符号は変換失敗とする。
対応外と判定できる既知の形式と、意味を理解できない入力を区別する。

和了判定・向聴数、流し満貫を得点計算の和了ケースとして抽出する処理、
雀魂、再開時の部分牌譜、任意の XML 断片列、並列処理、追記・再開は対象外。
`RYUUKYOKU` は局の終了として処理し、scoring ケースは作らない。

## 入力の契約

### ファイルと探索

- CLI は一つのファイルまたはディレクトリを受け取る。
  ディレクトリでは再帰的に対象ファイルを探索する。
- 対象拡張子は `.xml`、`.mjlog`、`.xml.gz`、`.mjlog.gz` とする。
  拡張子の判定は大文字小文字を区別しない。
- gzip のマジックバイトで圧縮を判定する。
  `.mjlog` の gzip にも対応し、`.gz` なのに gzip でない入力は失敗する。
- 展開後は一つの `mjloggm` 文書を要求する。
  XML 宣言のない文書は受理するが、ルートのないイベント列を自動補修しない。
  XML のエンコーディング宣言に従い、DOCTYPE・実体宣言は受理しない。
- ファイル指定では非対応拡張子を引数エラーにする。
  ディレクトリ内のその他のファイルは対象外とし、入力牌譜数に数えない。
  対象ゼロはエラーにする。探索・読み出しの権限エラーも無視しない。
- シンボリックリンクとディレクトリ junction は探索しない。
  入力と出力の包含関係は事前に検査し、入力内への出力を拒否する。

探索順は、入力ルートからの相対パスを `/` 区切りにした文字列の昇順とする。
一牌譜内は XML 子要素の順とし、ケースもその順で出力する。
探索順の決定にはファイル名一覧を保持してよいが、牌譜本体を全件保持しない。

### 牌譜 ID と重複

ファイル名から上記拡張子を取り除いた文字列を `log_id` とする。
空の ID は拒否する。標準的な天鳳 ID の形式への書き換えや補完はしない。
ファイル名が元の ID と違う場合は、一ファイル指定の `--log-id` で
原値を明示できる。ディレクトリ指定との併用は引数エラーとする。

同じ ID の入力が複数ある場合は `duplicate_log_id` で処理全体を失敗させる。
探索時に検出し、同じ ID の `.xml` と `.mjlog` を二重に変換しない。
牌姿の重複排除は行わない。
SQLite 対応時は DB の ID をそのまま使い、同じ変換コアへ渡す。

## 処理の分割

```text
ファイル入力（将来は SQLite）
  → 牌譜 ID と XML バイト列
  → XML の構文・必須属性の検査
  → ルール識別
  → イベント順の局面復元
  → 和了記録の正規化
  → corpus.parse_case
  → corpus.write_dataset
```

| モジュール案 | 責務 |
| --- | --- |
| `sources.py` | 探索順、ID、圧縮と入力の読み出し |
| `parser.py` | XML を位置付きイベントへ読み、属性・整数列を検査する |
| `rules.py` | GO の解釈、対応範囲、段位戦のルール適用 |
| `melds.py` | 天鳳の副露コードと物理牌 ID の復号 |
| `reconstruction.py` | INIT からの局状態と和了状況の復元 |
| `scoring.py` | 天鳳の役 ID、期待値と比較条件の正規化 |
| `conversion.py` | 一牌譜の進行処理と AGARI からのケース抽出 |
| `datasets.py` | 複数牌譜の集計、診断、データセット出力の調整 |
| `cli.py` / `errors.py` | 引数、診断の表示、終了コード／変換エラー |

これは責務の目安であり、各モジュールの内部関数はテストで固定しない。
内部イベントには XML 子要素の 0 始まりの `index`、タグ、属性を持たせる。
コメント・空白はイベントに数えず、無視するメタデータ要素も位置には数える。
イベントのフィルタ後に採番し直さない。

`SHUFFLE`、`UN`、`TAIKYOKU`、`BYE` は意味を確認したメタデータとして扱う。
`BYE` 自体を対局終了とせず、その後の進行も処理する。
`GO`、`INIT`、ツモ・打牌、`N`、`REACH`、`DORA`、`AGARI`、
`RYUUKYOKU` は進行へ反映する。タグは厳密に分類し、たとえば
`DORA` を先頭文字だけで打牌と誤認しない。
未知の属性は正規化に必要な属性を置き換えるものとは解釈しない。
原文を診断できるよう残し、進行の意味を変える拡張は対応確認を必要とする。

## ルール・牌・副露の変換

### ルールと局

`GO.type` とロビー情報から、人数・赤・喰い断・対局種別を判別する。
人数は `player_count = 3 if (game_type & 0x010) != 0 else 4` とする。
マスク結果そのものは 0 または 16 であり、1 と比較しない。
ビットを 0/1 に取り出すなら `(game_type & 0x010) >> 4` とする。
この規則はユーザー指定と追加三麻牌譜の `type="185"` で確認した。
`GO` 欠落や必要なルール情報の欠落を、標準設定で補わない。
ビットの対応と受理する組合せは fixture で固定する。
段位戦・赤あり・喰い断ありを確認した入力だけを
`ruleset="tenhou-ranked-match"` にする。
卓ランクや東風／東南はルール識別のため解析するが、共通ケースの
新フィールドにはしない。元の `GO` 属性は出典情報に保持する。

四麻・三麻とも `INIT.seed[0] // 4` が場風、`% 4 + 1` が局番号、
`seed[1]` が本場、`seed[2]` が開始時の供託、`oya` が親席となる。
場風の表現範囲を超える値や無効な席は失敗とする。
追加三麻牌譜では東三局が 2、南一局が 4 で、3 を飛ばすことを確認した。
三麻の局番号は 1〜3、席は 0〜2 とし、四枠の符号化と区別する。
`INIT.ten`・`AGARI.sc` などの四席分の配列は、未使用席 3 の点数・増減が
0、`hai3` が空であることを確認し、共通の点数配列は三席分にする。
席 3 に行為や非ゼロの点数があれば不整合として失敗し、黙って捨てない。
元の四席分の文字列は出典情報に保持する。

### 牌と和了手牌

物理牌 ID 0〜135 は、牌種 `id // 4` と同種内の番号に分解する。
赤ありの入力では 16・52・88 を `0m`・`0p`・`0s` とし、
他は `1m`〜`9s`、`1z`〜`7z` にする。
範囲外や、和了手牌・副露内で重複する物理牌は失敗とする。

`AGARI.hai` は副露を除く和了牌込みの手牌として読み、
`machi` と一致する物理牌をちょうど一枚取り除いて `concealed_tiles` とする。
牌種が同じだけの別の牌を取り除かない。残った牌の順序は維持する。
`machi` が存在しない場合に補ったり、手牌から和了牌を推測したりしない。
和了者・放銃者は `who`・`fromWho` から取得し、同席ならツモとする。
進行の直前の牌・提供者と一致することも確認する。

ドラ・裏ドラ表示牌は `AGARI.doraHai`・`doraHaiUra` から取得する。
ドラ枚数を得点計算して期待役へ足さない。
通常のドラ表示牌は `INIT`・`DORA` の進行とも照合する。
裏ドラ属性がない場合の空配列への変換は、対象形式で「表示なし」を
意味することを fixture で確認する。必要な表示牌の欠落とは区別する。

### 副露

`N.m` と `AGARI.m` に同じ復号を使い、種別、物理牌配列、
鳴いた牌の位置、鳴き元の絶対席を求める。
コード中の相対席を、そのまま `from_seat` に保存しない。

天鳳コードには XML 上の牌配列がないため、配列順はコードの
牌スロットの順と定義する。表示向けに鳴いた牌を先頭へ移動したり、
`mpsz` への変換後にソートしたりしない。
各種別のビットとスロット順は、下記の復号方針に従い具体例で固定する。
暗槓の鳴き元は両項目とも `null`。
加槓は元のポンを更新し、元の鳴いた牌・相手を保持する。
元のポンと対応しない加槓は失敗とする。
抜き北コードは `melds` へ入れず、和了者の抜いた物理牌を追跡して
`nuki_count` にする。`AGARI.m` に含まれる抜き北とも照合する。

和了者の副露は進行から復元したものと `AGARI.m` を照合する。
最終ケースでは `AGARI.m` から抜き北を取り除いた副露の相対順を保持する。

### 副露コードの解読方針

[みちのいに!! の解読記録](https://m77.hatenablog.com/entry/2017/05/21/214529)
を基に、`m & 0x0004`（チー）、`0x0008`（ポン）、
`0x0010`（加槓）、`0x0020`（抜き北）、残り（槓）の順で分類する。
抜き北の物理牌は `m >> 8`。槓も上位バイトから牌を取り、
下位二ビットが 0 なら暗槓、それ以外は大明槓として復号する。
チーとポン・加槓は、それぞれのパターンと同種内番号を分けて読む。
式の各スロットは実装時の小さな入力・期待牌配列で固定する。
追加三麻牌譜の `m=41514` は `0x0008` と `0x0020` の両方が立つがポンであり、
抜き北のビットだけを先に検査してはならない。

鳴き元は四麻・三麻とも `(who + (m & 0x0003)) % 4` とする。
三麻でも `% 3` に変更しない。追加牌譜の要素 376 では
`who=1, m=27211` で席 0 の打牌をポンしており、
下位二ビットの 3 を四席基準で解釈すると一致する。
得られた絶対席が三麻の未使用席 3 を指す場合は失敗する。

[Project Re:Now の mjlog 資料](https://kyphd.github.io/renow-docs/renow/mjlog/)
もイベント・ビット配置の参照先とする。
両資料には推測・未検証箇所や牌種順の記述の揺れがあるため、
牌種は本書の `m, p, s, z` の ID 順に統一し、実記録と照合する。

### 三麻の牌と抜き北

- 二萬〜八萬は使用しない。牌 ID は詰め直さず、元の 0〜135 の体系で読む。
- チーは受理しない。北の手牌・副露での使用と抜き北を区別し、
  北が手牌にあるだけでは `nuki_count` を増やさない。
- 抜き北は 0〜4 枚。抜いた牌が北（ID 120〜123）であることと、
  手牌・副露内の北との物理牌の重複を検査する。
- 抜き北は新しい通常副露や槓ではなく、抜きの宣言と補充ツモとして追跡する。
  補充ツモ前に抜いた北でロンされる可能性も扱う。
- 抜き北による一発・地和・ダブル立直の中断は
  [公式三麻ルール](https://tenhou.net/man/index.html#RULE) に従う。
  和了打診前に一発を消してしまわず、成立・補充ツモへ進むタイミングを区別する。
- 三麻の山と補充牌の管理は四麻と分ける。抜き北を通常ツモ・槓の
  どちらかへ一括変換せず、嶺上・海底・槍槓の各判定へ明示的に反映する。
  詳細は実牌譜 fixture で確認する事項に残すが、初期実装の完了条件に含める。

## 和了状況の復元

初期実装では全員の物理牌の所持も追跡する。
和了形や行為の全合法性は判定せず、手番・所持牌・消費牌と記録の対応を検査する。
局開始、ツモ・打牌回数、鳴き、立直、直前の牌と行為、
槓・抜き北と補充ツモ、生牌の残数、ドラ表示の更新を追跡する。
状況と矛盾する `AGARI` や、終局のない局を受理しない。

| 項目 | 復元の方針 |
| --- | --- |
| `riichi` | `REACH` の宣言と成立を区別する。ダブル立直は最初の打牌と、それ以前の鳴きの有無から判定する |
| `ippatsu` | 立直成立後から次の自己打牌までを追跡する。次のツモでの和了も含め、鳴き・槓・抜き北による中断と和了打診の順序を反映する |
| `rinshan` | 通常ツモ・槓の補充ツモ・抜き北の補充ツモを区別し、対象ルールを適用する |
| `chankan` | 加槓・抜き北の宣言から成立・補充ツモまでの窓を追跡し、通常の放銃と混同しない。対象ルールでは暗槓へのロンは認めない |
| `haitei` / `houtei` | 通常ツモの残数と最後の打牌を追跡し、槓による山の変化と嶺上・槍槓との区別を反映する |
| `tenhou` / `chiihou` | 親の最初のツモ、子の最初のツモ、それ以前の鳴き・抜き北の有無から判定する |
| `renhou` | 対象の段位戦ルールでは常に `false` |

立直宣言牌でのロンは成立前の処理として扱い、供託を先に加算しない。
一発を自己ツモの到来だけで消してはならない。
槍槓・抜いた北へのロンの対象牌は `machi` と照合し、
`discarder_seat` はその提供者。
加槓・抜き北の成立を先に確定して、和了打診時点の一発などの状態を
失わないようにする。暗槓へのロンは国士無双でも対象ルールと矛盾するため拒否する。
残数の初期値と槓ごとの更新規則は、海底・河底の fixture と一緒に固定する。

`situation_provenance.method` は `event_reconstruction` とする。
`event_indices` は当該局の `INIT` から当該 `AGARI` までの全子要素の
位置を昇順で保存する。まずは根拠の最小化より監査の容易さを優先する。

完全な進行があれば既知の値を保存する。進行が破損している場合は
牌譜全体を失敗とし、全項目を `null` にして通過させない。
構造は正しくても形式上判別できない個別状況に限り、corpus の規約に従い
`null` と `unknown_fields` の理由を対で保存できる。
その例外は fixture と文書で根拠を追加してから採用する。
対応をまだ実装していないことを「出典が不明」として出力しない。

## 期待値と出典の保持

### 役・翻・符・区分

`yaku` は ID・翻の対、`yakuman` は役満 ID の列として解析する。
未知の役 ID は `unknown_yaku_id` で失敗し、一部だけの内訳を出力しない。
全対応表は converter 内に置き、[共通の役 ID](corpus-yaku.md) に対応させる。
通常役は記録された翻を保存し、翻数が 0 の裏ドラ項目は内訳から除く。
通常役の合計翻は記録された翻の和として正規化する。
役満の翻は `null`、単独の倍率は 1、複合倍率は記録された役満の個数とする。
単独ダブル役満用の corpus ID があっても、天鳳の倍率を 2 に補正しない。

ローカル XML で確認できた ID は次のとおり。
実装の `scoring.YAKU_IDS` には、参照資料の役配列を基に ID 0〜54 の
対応表を定義した。全役の実牌譜照合は追加検証として残す。

| 天鳳 ID | corpus ID |
| --- | --- |
| 0 / 1 / 2 | `menzen_tsumo` / `riichi` / `ippatsu` |
| 7 / 8 / 9 | `pinfu` / `tanyao` / `iipeikou` |
| 12 | `jikaze_sha` |
| 47 | `kokushi_musou` |
| 52 / 53 / 54 | `dora` / `ura_dora` / `aka_dora` |

追加三麻牌譜では抜き北を持つ和了でも `yaku` は上記 ID 52〜54 を使う。
出典の `dora` の翻を保持し、抜き枚数から期待役 `nuki_dora` を追加したり、
記録されたドラ翻を分割したりしない。入力の `nuki_count` は別に復元する。

`ten[0]` は符として原値を保存する。国士無双の 0 符も変更しない。
`ten[2]` の 0〜4 は順に `below_mangan`、`mangan`、`haneman`、
`baiman`、`sanbaiman` とする。
5 の場合は、役満 ID があれば `yakuman`、通常役の記録で役満 ID が
なければ `kazoe_yakuman` とする。役データ自体の欠落を数え役満と解釈しない。
既知の記録同士の矛盾は失敗とし、再計算で修正しない。

### 点数と支払い

- `ten[1]` は本場・供託を除く和了者への支払総額として `base_points` にする。
  麻雀の基本点へ変換しない。
- `sc` の席ごとの点数・増減の対を読み、増減を 100 倍して
  `event_score_deltas` に保存する。`ten[1]` をさらに 100 倍しない。
- 単独和了で各増減がその和了に対応すると確認できる場合、
  他家の負の増減を正の `payments_by_seat` にし、和了者は 0 とする。
  和了者の正の増減を `winner_gain` にする。
- 支払いの和から `base_points` を引いた値を `honba_points`、
  `winner_gain` から支払いの和を引いた値を `riichi_stick_points` とする。
  記録の分解であり、符・翻から点数を計算する処理ではない。
- `ba` の本場・供託と進行を照合し、負の成分や記録の矛盾は失敗とする。
  `round.riichi_sticks` は和了の精算直前の場の本数とし、開始時の値を
  無条件にコピーしない。

三麻の点数配列は三席分とし、ツモは実際の二人分の支払総額を保存する。
四人目の支払いを足して四麻相当に補正しない。
追加三麻牌譜のロンでは一本場 200 点を確認したため、
四麻の 300 点を共通の定数として使わない。
期待値の本場分は引き続き実際の増減から分離し、人数別のルールと照合する。

連続する `AGARI` は同じ局の和了群としてまとめ、群の直前の状況を保持する。
群の途中で供託・一発・直前の打牌をリセットしない。
各 `AGARI` は別イベントなので `source.winner_index=0`、
`source.event_index` はそれぞれの位置、`win_number` は局内の順序で 1 始まり。
天鳳の `sc` を雀魂のような和了群全体の増減と決めつけず、
個々の記録が示す範囲を実例で確認する。
三家和了の `RYUUKYOKU` から三件の和了を生成しない。

複数ロンの本場・供託の帰属を「先頭の AGARI」という仮定だけで決めない。
各記録と群の前後の点数から一意に確認できる値だけを分解する。
帰属が不明な値は `null` と理由付きの比較除外にする。
役・符・素点など独立して確認できる値は保持する。

責任払いは `paoWho` を出典に残す。記録から支払いを分離できれば保存し、
`payments_by_seat` は `liability_payment` で比較除外する。
分離できなければ同項目を `null` とし、その理由も保持する。
責任払いを理由に和了ケース全体や既知の役・素点まで除外しない。

### 比較条件・監査用情報

比較除外は `expected` 直下のフィールド単位とする。
国士無双の符は保存しつつ `kokushi_fu_not_comparable` で除外する。
他の役満の符は、記録があれば比較し、未記録なら `null` と
`not_recorded` を保存する。不明な期待値を 0 や空配列に置き換えない。

`source.scoring_values` は `AGARI` の全属性を元の文字列で保持し、
追加の `GO` キーに元の GO 属性辞書を保存する。
元の役 ID・副露コード・`ba`・`sc`・`paoWho` も追跡できる。
名前や段位などの `UN` 属性は出力しない。
点数の未確定部分を生の記録から再確認できるようにする。

`case_id` は `tenhou:{encoded_log_id}:{wind}:{number}:{honba}:{win_number}`。
ID 部分は `urllib.parse.quote(log_id, safe="")` とし、
`source.log_id` は原値を保つ。詳細は [corpus の補完仕様](corpus-edge-cases.md)。
生成中に同一 case ID が生じた場合は、黙って上書きせず失敗する。

## Python API と CLI の方針

公開する変換 API は次の二つとする。
例外も `tenhou_converter` から import できる。

| API | 契約 |
| --- | --- |
| `convert_log(xml: bytes, *, log_id: str) -> list[ScoringCase]` | 展開済みの一牌譜を検査・変換する。正常な和了なしは空リスト。非対応は専用例外、不正は位置付きの変換エラー |
| `convert_files(input_path, output_directory, *, log_id=None, cases_per_file=100000, compress=True, report_path=None)` | 探索・集計・公開を実行し、成功時に corpus の Manifest を返す。失敗時は集計・診断を持つ例外を通知する |

`ConversionError` は `reason`・`message`・`event_index`・`field` を保持し、
既知の対応外ルールはその派生の `UnsupportedLogError` とする。
バッチの失敗は `BatchConversionError.report` に診断を保持する。
引数や出力先の事前検査は `ValueError`・`FileExistsError` などを返す。

ルートが閉じ、すべての局が `AGARI` または `RYUUKYOKU` で終了した XML を
受理する。局単位の抜粋も扱うため、対局終了の `owari` は必須にしない。
元の対局から局が丸ごと欠落しているかの検出は保証しない。

`convert_log` は一牌譜の終端まで確認してから返す。
途中の和了だけを成功として利用者へ渡さない。
バッチは一牌譜分の XML・ケースを保持し、処理済み牌譜を順に解放する。
全コーパス分のケースは保持しない。

以下のコマンドを提供する。

```console
tenhou-converter mjlog logs/tenhou --output data/tenhou-scoring
tenhou-converter mjlog sample.mjlog --log-id example-game --output data/example --no-compress
tenhou-converter mjlog logs/tenhou --output data/tenhou-scoring --cases-per-file 100000 --report artifacts/tenhou-conversion.json
```

出力はデフォルトで gzip、分割は corpus の既定と同じ 100,000 件とする。
`--cases-per-file` は正の整数、`--no-compress` は非圧縮 JSONL にする。
将来の `houou-db` サブコマンドは、DB スキーマの確認後に追加する。
初期実装に未動作のサブコマンドは登録しない。

CLI は最終集計を標準エラーへ出す。`--report` 指定時は UTF-8 JSON の
診断ファイルも保存する。既存 report の上書きは拒否し、出力内のパスも拒否する。
診断には版、入力・出力、生成条件、集計、ケース数、公開の成否と
牌譜別の理由・イベント位置・フィールドを含める。
詳細診断は一牌譜につき主原因一件とし、進捗から成功したかのように報告しない。
終了コードは 0 が公開成功、1 が変換・空出力・IO の失敗、2 が引数不正。

## 集計・失敗・公開

集計の単位は [manifest の契約](corpus-manifest.md) と同じ入力牌譜とする。
一つの牌譜を converted / failed / excluded のいずれか一つに分類する。
11 和了でも converted は 1。正常に終了した和了なしの牌譜も converted は 1。
その牌譜の最後まで確認してから converted を加算する。
一つでも変換できない和了があれば牌譜全体を failed とし、ケースは返さない。

| 分類 | 理由コードの例 | 処理 |
| --- | --- | --- |
| 意図的な除外 | `unsupported_rules` | 件数と理由を残して次の牌譜へ進む |
| 入力の失敗 | `invalid_xml`, `invalid_attribute`, `incomplete_log`, `inconsistent_events` | 当該牌譜のケースを破棄して次へ進む |
| 意味が未対応 | `unsupported_xml_version`, `unknown_event`, `unknown_yaku_id`, `unknown_meld_code` | 不明な値を代入せず失敗にする |
| corpus への不正な変換 | `invalid_case` | CorpusError のフィールドと元イベント位置を診断に残す |

入力読み出しの失敗も該当牌譜を failed とする。
出力 IO、探索自体の失敗、予期しないプログラムの例外は処理全体を中止し、
処理していない牌譜を converted や excluded に数えない。
診断に集計が最終値か途中値かを明示し、途中値から完成 manifest を作らない。
`except Exception` で実装上の不具合を意図的な除外に変換しない。

`corpus.write_dataset` にケース列と更新可能な conversion 辞書を渡す。
既存出力は入力消費前に拒否し、親ディレクトリは呼び出し側で用意する。
writer が一時ディレクトリへ出力し、全入力処理後の集計を検査して公開する。
failed が一件でもあれば公開しない。正常ケースだけの「部分的な成功」を
完成データセットとして出さない。空入力・全除外・全件和了なしも公開しない。
意図的な除外だけがあり、有効なケースが残る場合は、除外を記録して公開できる。

失敗時の診断は出力データセットと別の `--report` または標準エラーに残す。
失敗を含む manifest を成功したデータセットの場所へ置かない。
中断や診断ファイル自体の IO 失敗時は、保存できた診断と公開状態を可能な範囲で
通知する。診断ファイルとデータセットの二か所を同時に原子的更新する契約は持たない。

`generator.name` は配布名と同じ `tenhou-converter`、
`version` はパッケージの実際の版。
`settings` には入力経路、対応ルールの選択条件、ID の取得規則、探索順、
分割件数・圧縮、状況復元方針の版を記録する。
同じ入力・版・設定でケース内容・ID・順序を再現できることを保証対象とする。
gzip バイト列の一致は保証せず、manifest のハッシュは実際の保存バイト列から得る。

## 現時点の根拠と確認する事項

### ローカルで確認した範囲

Git 管理外の `logs/tenhou/<masked-log-id>.xml` を読んだ。
ルートは `mjloggm ver="2.3"`、GO は `type="41", lobby="0"`、
INIT は 12 件、AGARI は 11 件、RYUUKYOKU は 1 件。
門前ロン・ツモ、副露、赤、国士無双、立直・成立を含む。
最初の和了と国士無双は既存の corpus 例とも対応する。

- 要素 103: `ten="40,2600,0"`、立直・一発。
  `sc` の増減から支払い 2600、収入 3600、供託 1000 と分解できる。
- 要素 171: 親ツモ、`ten="30,1500,0"`。
  他家の増減は各 -500 で、`ten[1]` が支払総額であることを確認できる。
- 要素 536: 二つの副露コードを持つ和了。
  コードの全種別を検証できることまでは意味しない。
- 要素 1136: 国士無双、`ten="0,32000,5"`、`yakuman="47"`。
  本場 300・供託 1000 を含む収入 33300 が記録されている。

### 追加三麻牌譜で確認した範囲

`logs/tenhou/` に追加された XML は `ver="2.3"`、
GO は `type="185", lobby="0"`。INIT は 8 件、AGARI は 6 件、
RYUUKYOKU は 2 件、抜き北の N は 19 件。
`hai3=""`、点数配列の第4席は 0 で、局は 0・1・2・4 と進む。
以下の位置は元 XML 子要素の 0 始まりであり、牌譜 ID は文書へ載せない。

| 要素位置 | 確認内容 |
| --- | --- |
| 6 | `N who="0" m="31264"` は ID 122 の抜き北。直後に席 0 の補充ツモがある |
| 177 | 席 1 のロン、`m="30752"` は北 ID 120 一枚。素点 7700、本場 200、供託 2000、収入 9900 |
| 228 | 席 2 の子ツモ、`ten="40,2000,0"`。支払いは席 0 が 700、親の席 1 が 1300、供託込み収入 3000 |
| 333 | `seed[0]=4` は南一局で、三麻でも除数は 4 |
| 376 | 席 1 が席 0 の牌をポン。相対席 3 は `% 4` で解釈する |
| 492 | 親のロン、素点 12000、本場二本で 400、供託 2000、収入 14400 |
| 550 | `m="31520,31264,30752"` は北 ID 123・122・120 の三枚。通常副露は空、nuki_count は 3 |

これにより、六件とも `AGARI.m` を通常の副露だけとして読むと誤ることを確認した。
この牌譜の和了は抜き北を含むが、抜き北直後の和了・抜いた北へのロンの
全パターンを確認できたことは意味しない。

### 実装前または初期実装中に確認する事項

1. 全役 ID の対応、役満亜種の名前と倍率、数え役満の記録。
2. GO のビット・ロビー・省略属性と、受理する版・対局種別の具体例。
3. 全副露のビットと牌スロット順、赤を含む鳴き、加槓・槍槓のイベント順。
4. 槓による残数更新、海底・河底、ドラ追加と和了の順序。
5. ダブロンの各 `sc`・`ba` と本場・供託の帰属、責任払いの記録。
6. 対局全体が完結したかの厳密な判定が必要か。
   現行 API は閉じた XML と各局の終了を確認し、`owari` は要求しない。
7. 抜き北の補充ツモと海底・嶺上、抜いた北へのロンと槍槓の対応。
   一発を消すタイミングと和了打診、連続する抜き・槓の順序を fixture で確認する。
8. houou-logs DB のスキーマ・行選択条件・BLOB 圧縮・XML 文書か断片列か。

未確認の符号や精算に仮定を置いたまま対応済みにしない。
対応表と根拠となる小さな fixture を、テストを追加する段階で本書へ反映する。
独立した入力層の設計だけを先に行い、SQLite の列名を前身のコードから
恒久仕様として採用しない。
