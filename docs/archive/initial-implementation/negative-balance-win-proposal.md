# 包・複数ロンと負の持ち点の調査・修正案

調査日: 2026-11-16

実装日: 2026-11-21

本書は当初の調査・修正案と、その後の実装結果を記録する。

## 実装結果

- 和了群内で同じ増減が繰り返し記録され、開始残高も一致する `sc` を
  共有精算として扱う。他家に正の増減があるかだけでは判定しない。
  繰り返された増減の開始残高が異なる場合や、共有・個別として解釈して
  整合しない記録は拒否する。未確認の記録形式を推測で補完しない。
- 共有精算は和了者の差し引きが負・ゼロでも保持する。
  個別の本場・供託・収入・支払いは `null` とし、
  `multiple_ron_allocation_unknown` の比較除外を付ける。
  既存の `liability_payment` の理由は維持する。
- 供託総額、和了者以外への収入、素点とボーナスの整合性を群単位で検査する。
  和了者同士に包がなければ本場を含む支払い総額を照合する。
  和了者が責任者でもある場合は相殺額の範囲を検査するにとどめ、
  複合役満の包の対象額やボーナス受取人を推測して確定しない。
- `INIT.ten` から成立済み立直の支払いを引き、最初の `sc` の残高を照合する。
  個別精算は順に、共有精算は一度だけ反映し、途中残高と次の `INIT.ten` を
  照合する。精算中の負残高で二人目の和了を打ち切らない。
- corpus のモデル・収入の非負制約と validator の部分比較方針は維持した。
  既存機能で対応できるため、この二パッケージには回帰テストと合成例を追加した。

新しい三麻の XML fixture は、三元牌を南家から順にポンした東家の大三元と、
西家の同じ放銃牌への南家のロンを記録する合成例。
東家の個別精算後の南家残高は -14000 点とし、南家の収入は 3200 点とした。
南家は門前混全帯么九 2 翻、符は 20 + 門前ロン 10 + 么九暗刻 8 +
場風雀頭 2 + 単騎 2 = 42 を切り上げた 50 符。
ドラ表示牌は `7p` とし、両手牌に不要なドラを加えない。
共有増減は `[48000, -20800, -27200]` となる。
これらの期待値は手作業で設定し、検証対象ライブラリの出力から生成していない。

元のスクリーンショットの牌譜 ID は未特定のままであり、
天鳳の当該実牌譜の `sc` 形式や、精算後の飛び判定は未確認。
今回の対応は合成入力での変換・保存・部分比較の検証である。

検証結果:

- 全体テスト 604 件成功、既存の環境依存テスト 1 件スキップ。
- Ruff の lint・format、ty、差分の空白検査が成功。
- 三パッケージの sdist・wheel ビルドが成功。
- corpus と converter の wheel を独立環境へ依存解決付きでインストールし、
  負残高からの二件目の和了を変換できることを確認した。
- XML → manifest 付きコーパス → validator の結合確認は、
  個別・共有の両形式で二件とも部分比較が passed。
  共有精算の個別収入は excluded、イベント全体の増減は unsupported となることを確認した。

## 対象と未確認事項

報告された状況は、天鳳の鳳凰卓・三人麻雀で東家の大三元の責任者が南家となっており、
西家の放銃に東家・南家がロンし、東家の精算後に南家の持ち点が負になっても
南家の精算が続くというもの。

サービスと卓種別はユーザーの補足により特定された。
スクリーンショットは匿名化されていたため、牌譜 ID は未特定。
元の画像・牌譜は本調査では直接確認していない。
上家取りによる精算順は報告された画面上の観測として扱い、他のサービスの仕様や
天鳳 XML の `AGARI` の記録順に一般化しない。16000 点という条件だけから正確な支払額を
確定しない。以下の金額は、挙動を切り分けるための合成値である。

同じ放銃に対する和了群の精算継続と、その後の飛び判定・次局続行は別問題。
今回の対応では対局終了ルールを追加せず、記録された和了を抽出する。

## 当初の調査時点での各パッケージ

| 対象 | 確認結果 | 制約・必要な対応 |
| --- | --- | --- |
| corpus | 負の持ち点を `source.scoring_values` に保持でき、`event_score_deltas` も負数を許容する | 共通入力に持ち点の専用フィールドはなく、途中残高・飛び判定は検証しない |
| tenhou-converter | 個別精算の `AGARI.sc` では、精算前の持ち点が負でも期待値を抽出できる。連続する二件目の和了も処理する構造 | 包の支払いと和了収入を相殺した共有 `sc` の判定・分解に不備がある |
| mahjong-validator | 持ち点を計算入力にせず、各和了の役・符・点数を検証する | 包の席別支払いは比較除外。イベント全体の移動は unsupported。途中残高・精算順・飛びは検証しない |
| majsoul-converter | 未実装 | 今回の天鳳の観測の直接の対象ではない |

### corpus

`packages/corpus/src/corpus/models.py` の `ScoringInput`・`Round` に
持ち点はない。出典固有の記録は `Source.scoring_values` に保持する。
`checks._bounds()` の `winner_gain >= 0` は「この和了による収入」の制約であり、
「和了時の持ち点」の制約ではない。これを緩める必要はない。

`checks._points()` は個別の収入と点数成分、個別の支払い総額を検査する。
イベント全体の差し引きには `event_score_deltas` を使うため、和了者が
別の和了の責任者となって全体では支出超過でも、現行のモデルで表現できる。
個別値を分離できなければ `null` と比較除外理由を記録できる。

### tenhou-converter

`scoring.expected_values()` は `sc` の持ち点部分に非負制約を設けていない。
`conversion.convert_log()` は一件目の和了後も `AGARI` を受け取り、
`RoundState.situation()` は同じ放銃牌に対する二人目の和了を扱う。
和了の精算で持ち点を更新して飛び判定する処理はない。

一方、共有精算の検出は「現在の和了者以外に正の増減があるか」に依存する。
包で他の和了者が支出超過・差し引きゼロになると検出できない。
また、共有精算でも、共有判定による値の除外より前に
`payments[who]` と支払総額を検査する。
そのため、和了群全体の差し引きが負の和了者を
`winner must not pay their own win` として拒否する。

`RoundState.check_settlement()` は供託・本場を照合するが、
席ごとの残高推移や `sc` の持ち点と前後の残高との一致は検査しない。
総額だけが一致する誤った席別分解は検出できない場合がある。

`RoundState._check_scores()` は局開始時の `INIT.ten` が負だと拒否する。
今回の局中の一時的な負数とは別の制約であり、今回の観測だけを根拠に
撤去しない。負数のまま次局を開始する牌譜に対応するなら別途判断する。

### mahjong-validator

`adapter.prepare_hand()` は持ち点を渡さず、`normalize_result()` は
個別和了の点数・収入・支払いを生成する。
責任払いの席別支払いは変換器の `liability_payment` 指定で比較除外する。
`validation._unsupported_fields()` は `event_score_deltas` を unsupported とし、
共有精算や本場・供託付きの後続ロンでは個別配分も検証対象から外す。

したがって「負の持ち点から和了したため計算できない」という問題はないが、
このケースの精算全体を正しいと保証する機能もない。
他項目が一致してケースが passed でも、精算全体の検証成功を意味しない。

## 当初の調査で実行した切り分け

コードを保存しない Python 入力で `expected_values()` を直接呼び出した。
席順は東・南・西。全例で本場・供託はゼロ、三麻の未使用四席目はゼロとした。
これは点数抽出の実験であり、実牌譜変換や観測されたサービスの再現ではない。

合成条件は、開始持ち点 `[50000, 10000, 45000]`、
東家の和了収入 48000、南家・西家の支払い各 24000、
続いて南家の和了収入 1000、西家の追加支払い 1000 とした。

| 入力 | 修正前の結果 |
| --- | --- |
| 東家の個別 `sc="500,480,100,-240,450,-240,0,0"` | 収入 48000、支払い `[0,24000,24000]` として受理 |
| 南家の個別 `sc="980,0,-140,10,210,-10,0,0"` | 精算前残高 -14000 を拒否せず、収入 1000 として受理 |
| 東家に共有 `sc="500,480,100,-230,450,-250,0,0"` | 共有と認識せず、支払い `[0,23000,25000]` と誤分解。席別支払いの比較除外は付く |
| 南家に同じ共有 `sc` | `inconsistent_events: winner must not pay their own win` で拒否 |

共有値の南家 -23000 は、責任払い -24000 と和了収入 +1000 の合算であり、
南家が自分の和了に支払ったことを意味しない。

corpus の既存ダブロン fixture のコピーに、負の `old_scores` と
和了者が負になる `event_score_deltas` を指定し、`parse_case()` の受理を確認した。

既存の関連テストは以下の 75 件が成功した。

```console
.venv/Scripts/python.exe -m pytest packages/tenhou-converter/tests/test_scoring.py packages/corpus/tests/test_edge_cases.py packages/validator/tests/test_comparison.py -q
```

## 当初の修正案

まず corpus の既存の意味を維持し、変換器の共有精算の解釈を直す。
個別の `winner_gain` を負数許容に変える案は採らない。

1. 連続する和了群の記録を参照して、`sc` が個別精算か共有精算かを判定する。
   他家の正の増減の有無だけでは判定しない。`who`・`fromWho`・`paoWho`、
   各 `sc` の持ち点・増減、`ten`・`ba` と群の前後を確認する。
   実牌譜で形式を確認し、一意に解釈できないものを個別精算と推測しない。
2. 共有精算の差し引きを `event_score_deltas` に保持する。
   個別の収入・支払いを記録から一意に分離できない場合は、
   `winner_gain` を含む該当フィールドを `null` とし、理由付きで比較除外する。
   共有差し引きをそのまま個別収入・支払いに転用しない。
   既存の個別記録の抽出は維持する。
3. 「和了者は自分の和了に支払わない」などの検査を個別精算へ適用する。
   共有精算では和了者の差し引きが負・ゼロでも許容し、供託総額や
   記録された残高の整合性を群単位で検査する。
   共有記録を複数ケースへ保存しても総額を二重計上しない。
4. corpus には合成の包＋ダブロン例を加え、個別収入が正で
   群全体の和了者の差し引きが負でも読み書きできる契約を明示する。
   途中残高を共通化するスキーマ拡張は今回の修正には必須ではない。
5. validator は現在の部分比較を維持し、追加例で除外・unsupported と
   検証可能な役・符・素点を確認する。群単位の精算検証を新機能として
   実装するかは別途検討し、今回必須の修正に含めない。

調査時点では共有形式を確認できる実牌譜がなく、具体的な判定条件は未確定だった。
合成例で表現能力と誤判定を検証することと、実サービスへの対応完了を区別する。
