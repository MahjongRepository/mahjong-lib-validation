# corpus パッケージの設計

決定日: 2026-11-01

本書は、[プロジェクト構成と設計方針](architecture.md) を具体化する、
corpus パッケージの決定事項を記録する。
未決事項は実際の牌譜を基に JSON 例を作りながら確定する。
本書の名前や構成は設計であり、実装済みであることを示さない。

## パッケージと開発環境

- ディレクトリは `packages/corpus/`、配布名は `corpus`、
  import 名は `corpus` とする。
- このプロジェクト内で利用し、PyPI への公開は予定しない。
- 対応 Python は `mahjong` に合わせて 3.10〜3.15 とする。
- `src/` レイアウトと `uv_build` を採用する。
- 単体テスト・静的検査はルートの `dependency-groups` に指定された
  ツールを使用する。現時点では pytest、ruff、ty が該当する。
- 実装は [実装・テスト方針](development.md) に従う。

corpus は、共通モデル、読み書き、形式・整合性の検査を担う。
`mahjong` や個別の変換器には依存しない。
最初は scoring を扱うが、パッケージ名を得点計算に限定せず、
将来の和了判定・向聴数のケースにも共通する処理の置き場とする。

## 対応範囲と責務

- 天鳳段位戦ルールと雀魂段位戦ルールを対象とする。
- 四人麻雀・三人麻雀の両方と赤牌に対応する。
- 一件の scoring ケースは、一人の和了を表す。
  ダブロン・トリプルロンは和了者ごとに別ケースとする。
- 責任払いも表現できるようにし、保存できる情報と、
  検証対象に対して比較できる情報を区別する。
- 雀魂の情報も考慮して共通モデルを設計するが、
  雀魂変換器の実装時期は全体設計に従い将来の対応とする。

## 牌・手牌・副露

- 牌は `mpsz` 表記とする。赤牌は `0m`、`0p`、`0s` で表す。
- 手牌には和了牌と副露を含めず、和了牌は別に保持する。
- 副露は種別と `mpsz` 表記の牌の配列で表す。
- 副露の牌の配列は元牌譜の順序を保持し、ソートしない。
  たとえば雀魂では鳴いた牌が最後になる並びを保持する。
- 抜き北は枚数を保持する。

副露の種別名、鳴いた牌・相手の明示方法、原形式ごとの順序の
解釈方法は JSON 例を作る際に具体化する。

## 場況とルール

場況は数値と文字列で表す。
ルールは `tenhou-ranked-match` のような識別子で表す方針とする。
具体的なフィールド名、席・場・局の数値の起点と文字列表記は未決。

四麻・三麻は必ず識別できるようにする。
ルール識別子に人数を含めるか、別プロパティで表すかは未決であり、
`ruleset` と `player_count` に分ける案が出ている。
元牌譜から人数を判別する方法は変換器の責務とする。

## 進行記録からの和了状況の復元

変換器が進行記録から和了時の状況を復元し、その結果を
コーパスに保存する。コーパスの利用側で元牌譜を読み直す必要はない。
役一覧から推定した和了状況は別途保持しない。

復元対象は、ロン・ツモ、立直・ダブル立直、一発、嶺上開花、
槍槓、海底摸月、河底撈魚、天和、地和など、
得点計算の入力に必要な和了状況とする。
槓・抜き北などの影響は対象ルールに従って扱う。
状況役の復元に必要な進行を追跡し、
手牌全体の毎巡の復元や行為の合法性判定までを必須にはしない。

和了状況と期待する役一覧は独立した情報として扱う。
たとえば、一発が有効な間に役満で和了した場合も、一発の状況を
入力に保持し、計算結果の役一覧に一発が加算されないことを検証できる。

復元できない状況は不成立の `false` と混同せず、
不明であることとその理由を表せるようにする。
各フラグ、復元元の情報、不明値の具体的な形式は未決。

## 期待値と比較条件

期待値は検証対象の `mahjong` で計算せず、牌譜の記録から取得する。
役、各翻数、合計翻、符、役満倍率、和了点、本場、供託、
個別支払い、点数移動など、牌譜から区別できる情報は分けて保持する。
未記録・不明・未対応・比較対象外と、ゼロを区別する。

比較対象外はケース全体を除外するだけでなく、項目ごとに理由を
付けられるようにする。次の比較条件を採用する。

| 条件 | 扱い |
| --- | --- |
| 責任払い | プレイヤーごとの支払額を比較対象外とする |
| 役満の符 | 記録されている場合は比較し、未記録の場合は比較対象外とする |
| 国士無双の符 | 記録の有無にかかわらず比較対象外とする |

役満だからという理由だけで符の比較を一律に省略しない。
国士無双の符について、天鳳は 0、雀魂は 25 という情報が
議論で挙がったが、具体値は未確認である。
実際の値が記録されていればそのまま保存し、比較条件とは分離する。

役の共通識別子、翻と役満倍率の構造、点数の各フィールド、
比較可否・理由の表現は JSON 例で確定する。

## ケースの識別

ケース ID は、次の情報を組み合わせる。

- 牌譜 ID
- 場
- 局
- 本場
- 同一局内の何個目の和了か

和了順によってダブロン・トリプルロンの各ケースを区別する。
ID の文字列形式、和了順の起点・順序の定義、
出典間の衝突を避ける方法と元イベントの位置の表現は未決。
同じ和了イベントに属するケースの関連を判別できるようにする。

## 保存形式と今後の具体化

スキーマは `v1` から開始する。
全体設計のとおり、UTF-8 の JSONL と `.jsonl.gz` に対応し、
データセット単位の情報を `manifest.json` に保持する。

次の事項は、JSON 例を作りながら確定する。

- 各フィールド名、型、必須・任意の区別。
- 場・局・席などの数値の起点、文字列表記。
- 役の共通識別子と出典固有の値の対応。
- 点数・支払いの意味と比較条件の具体的な表現。
- ケース ID とレコード・ファイルの順序。
- manifest の必須項目、ハッシュ対象、互換性、未知フィールドの扱い。

読み書き・検査の API、不正入力やエラーの詳細は、
TDD で具体的な振る舞いを検討する際に決める。
ファイル分割サイズなどの調整は実データを扱ってから検討する。

## 設計に用いる牌譜

次のローカル牌譜を JSON 例と変換仕様の検討に用いる。
`logs/` は Git 管理対象外であり、これらを必須テストデータとして
参照する実装はまだ定めていない。

- 天鳳: `logs/tenhou/<masked-log-id>.xml`
  - `AGARI` は 11 件。副露、ツモ、役満の例を含む。
- 雀魂: `logs/majsoul/<masked-log-id>.json`
  - デコード済み JSON。`RecordHule` は 10 件、和了者単位では 11 件。
  - 一つの `RecordHule.hules` に二人が入るダブロンの例を含む。

両牌譜の最初の和了は、記録上いずれも 40 符 2 翻・2600 点の
ロンであり、最初の JSON 例の候補とする。
