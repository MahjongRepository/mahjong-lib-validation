### 公開 API

`corpus` は実行時の外部依存を持たず、標準ライブラリで実装する。
モデルは JSON と同じ辞書・配列構造の `TypedDict` とする。
テスト用の牌譜由来データは `packages/corpus/tests/fixtures/` に置く。
文書の JSON 例からコピーしたデータを使用し、テストは `docs/` に依存しない。
牌は `corpus.models.Tile` の `Literal` で 37 種類の表記を列挙する。
手牌・和了牌・副露・ドラ表示牌に同じ型を使い、
実行時の牌表記の検査にもこの定義を使用する。
モデルの型は `corpus.models`、以下の入口は `corpus` から import できる。

| API | 振る舞い |
| --- | --- |
| `ScoringCase` | v1 scoring ケースの型。型注釈自体は実行時の検査を行わない |
| `parse_case(value)` | 型・形式・基本的な整合性を検査し、`ScoringCase` として返す。入力を変更しない |
| `read_cases(path)` | UTF-8 の JSONL を順次読み込み、各ケースを検査して返すイテレータ |
| `write_cases(path, cases)` | 各ケースを再検査して JSONL を出力する。成功時に出力先を置換し、書き込み件数を返す |
| `CorpusError` | 不正なデータを表す `ValueError`。`field`、`message`、`path`、`line` を保持する |

パスは `str` または `Path` で指定する。末尾が `.gz` なら gzip を使う。
reader は先読みして全件を検査せず、イテレータを進めた時点で処理する。
途中で処理をやめる場合、呼び出し側はイテレータを `close()` できる。
全件を読まなければ、後続の破損まで検出したことにはならない。

writer は出力先と同じディレクトリに一時ファイルを作成し、
全件の検査・書き込み・クローズが成功してから置換する。
入力ケースが不正、入力イテレータが失敗、書き込みが失敗した場合は
一時ファイルを削除する。親ディレクトリの作成は呼び出し側が行う。
空のファイルは読み書きできるが、検証成功やデータセット完成を意味しない。
存在しないパスやアクセス権などの OS エラーと gzip 自体の破損は、
標準ライブラリの例外として呼び出し側に通知する。

## 初期 v1 の検査方針

- 定義された全フィールドを必須とし、不明値は対応する項目の `null` で
  表す。状況の不明理由は `situation_provenance.unknown_fields` に保存する。
- 定義外のフィールドは拒否する。`source.scoring_values` の内部は
  出典固有の JSON 値として保持する。
- 整数と真偽値を区別し、未知の版・ケース種別・ルール名は拒否する。
- 副露の牌順は変えず、`chii` の連続性、ポン・槓の同一牌種、
  構成枚数と手牌枚数を確認する。赤と通常の五を合わせて四枚を超える
  手牌も拒否する。暗槓は鳴き元情報をともに `null` とし、
  明副露は元の鳴いた牌と他家の席を必須とする。
  加槓では元のポンの鳴き元情報を保持する。
- 席の範囲とロン・ツモの放銃者指定を確認する。
  ルール固有の行為の合法性や和了状況は再判定・補正しない。
  `renhou` に対するルールの適用も変換器の責務とする。
- 比較除外は初期段階では `expected` 直下のフィールド単位とする。
  未記録の期待値には理由付きの比較除外を必要とする。
  役満時の合計翻が `null` であることは、役満倍率による表現として認める。
  この理由不要の扱いは、合計役満倍率が既知で正の場合に限る。
  役内訳・合計役満倍率の `null` も、ほかの不明値と同様に理由を必要とする。
- 記録された役の翻・役満倍率の合計と点数の成分を照合する。
  得点計算や役の成立判定は行わない。役名は `YakuId` の `Literal` に従い、
  未定義の役 ID は拒否する。一覧は [共通の役 ID](corpus-yaku.md) に記録する。
- イベント全体の点数移動は席数だけを確認し、単独の和了者の収入や
  供託と等しいという検査をしない。複数ロンの意味を保持するためである。
- ID を生成・再構成・マスクしない。呼び出し側が渡した原値を保存する。

## TDD の確認記録

最初の API 未実装による失敗の後、不正な牌・席・手牌枚数・期待値を
受理してしまう失敗を確認し、対応する検査を追加した。
IO では二行目の位置情報不足、後続の不正ケースによる既存ファイルの
破損、gzip 未対応、UTF-8 デコードの先読みによる失敗を確認してから
実装した。テストが通る状態で、型検査と整合性検査の内部構造を整理した。

## 確認結果

- 開発環境の単体テスト: 73 件成功（title 追加後）。
- sdist を生成し、その sdist から wheel を生成できることを確認。
- wheel をインストールした独立環境の Python 3.10.22・3.15.2 で、
  それぞれ全 73 件成功。`site-packages` からの import と、
  実行時依存の宣言が空であることも確認した。
- Ruff の lint・format と ty の型検査が成功。

## Refactor の記録（2026-11-02）

manifest 実装後の Green を確認し、仕様を追加せず内部の責務を整理した。
公開 API の名前・引数・戻り値、JSON の形式、検査順序、
例外の項目・位置情報は維持する。

| モジュール | 責務 |
| --- | --- |
| `_validation.py` | ケースと manifest に共通する型・JSON 値・下限の検査 |
| `checks.py` | scoring ケース固有の牌・席・期待値の整合性検査 |
| `_fileio.py` | UTF-8 JSON のデコード、位置付き構文エラー、一時ファイルからの置換 |
| `case_io.py` | JSONL・gzip の逐次読み書き |
| `manifests.py` | manifest の整合性検査と一ファイル単位の読み書き |
| `datasets.py` | manifest に従うファイル処理とデータセットの公開 |
| `models.py` / `errors.py` | 共通のデータ型と例外 |

共通の検査を `checks.py` から分離し、manifest や dataset が
scoring 固有の検査モジュールの private 関数に依存する構成を解消した。
JSON のデコードと安全なファイル置換の重複は `_fileio.py` に集約した。
全ファイルを読む場合の改行正規化と、JSONL の物理行番号の違いは保持する。

書き込み件数は `write_cases` がシリアライズ時に数えて返す。
dataset 側の `_write_shard` とカウント用のジェネレータは廃止した。
当初は内部の `_write_cases` で件数を返し、公開 API は `None` を返していたが、
2026-11-07 に `write_cases` へ統合し、dataset も公開 API を使う形にした。
dataset の一ファイル分のパス・ハッシュ・件数の検査は `_read_file` に分けた。
各ファイルの検査と dataset 全体の処理を別々に読める構造にした。

既存テストや期待値は変更していない。各段階で 117 件成功、
実 symlink のテスト 1 件スキップを確認した。
変更前コードとの比較でも、公開関数のシグネチャ、JSONL の出力バイト列、
例外の項目・理由・行番号・原因、CR/CRLF の manifest のエラー位置、
生成したデータセットの manifest が一致することを確認した。

## 再点検による修正（2026-11-02）

役内訳が不明でも既知の合計を保存するため、`Expected.yaku` と
`Expected.yakuman_multiplier` に `None` を認めた。
内訳・合計がともに既知の場合だけ照合し、比較除外の指定で照合を省略しない。
通常役の翻の合計は、内訳に役満がないことを確認して照合するため、
合計倍率が不明でも、既知の内訳と合計翻の不一致を検出できる。
不明値の推定や補完は行わない。詳細と JSON 例は
[scoring コーパスの JSON 例](corpus-json-examples.md) に記録する。

和了者自身への支払いと、抜き北を含めた北の枚数超過も拒否する。
支払いは席数を確認してから和了者の値を調べ、点数成分の有無に依存させない。
北の枚数は手牌・和了牌・副露と抜き北を合わせて確認する。
ドラ表示牌を含む全可視牌の枚数や、ルール固有の行為の合法性を検査する
範囲へは拡張していない。

これは開発中の初期 v1 の仕様補完とする。フィールドは引き続き必須で、
既存の正しいケースは変更不要。不明値を含む新しいケースは旧 reader では
読めないため、更新後の corpus を使用する。
公開後の形式変更では版を更新する方針は維持する。
